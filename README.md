# Support Ticket Dashboard

A full-stack **Support Ticket Dashboard** built for the provided Web Application Developer technical assignment.

The implementation keeps the existing dashboard design while completing the assignment requirements: persistent ticket storage, backend-driven querying, validation, ticket updates, summary counts, responsive states, seed data, automated tests, and setup documentation.

## Stack

- **Frontend:** React 19 + Vite
- **Backend:** Node.js + Express
- **Database:** SQLite using better-sqlite3
- **Testing:** Node's built-in test runner + Supertest

SQLite was selected to keep local setup simple without requiring a separate database server. Search, filtering, sorting, and pagination are executed by SQL on the backend.

## Assignment coverage

- Create support tickets
- Required title, description, customer email, and priority validation
- Title maximum of 120 characters
- Valid email format
- Priority: Low / Medium / High
- Status: Open / In Progress / Resolved

- Automatic created and updated timestamps
- Search by title or customer email
- Status and priority filters
- Combined search + filters
- Newest / oldest sorting
- Backend pagination, 10 tickets per page
- Complete ticket details
- Persistent status and priority updates
- Dataset-wide summary counts
- Loading, empty, and error states
- Responsive desktop/mobile layout
- Meaningful HTTP status codes
- Consistent JSON API error format
- 25 seeded tickets with varied status and priority

- Setup, seed, API, test, design-choice, assumptions, limitations, and AI-usage documentation

Authentication, deployment, and advanced visual design are intentionally outside scope.

## Setup

Requirements: **Node.js 20+** and npm 10+ recommended.

From the project root:

```bash
npm install
npm run install:all
```

Seed the database:

```bash
cd backend
npm run seed
```

Start backend:

```bash
npm run dev
```

In another terminal, start frontend:

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`.

### Run both servers together

After installing root dependencies and both packages:

```bash
npm run dev
```

## Seed data

The seed script resets the local SQLite ticket table and creates **25 tickets** with varied statuses and priorities:

```bash
cd backend
npm run seed
```

The database is stored at `backend/data/support.db` and requires no external database server.

## API

Base URL: `http://localhost:4000/api`

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/health` | Health check |
| GET | `/tickets` | Search/filter/sort/paginate tickets |
| GET | `/tickets/summary` | Dataset-wide summary counts |
| GET | `/tickets/:id` | Get complete ticket details |
| POST | `/tickets` | Create a ticket |
| PATCH | `/tickets/:id` | Update ticket fields |

Example:

```text
GET /api/tickets?search=password&status=Open&priority=High&sort=newest&page=1&limit=10
```

### Error format

Validation failures use HTTP `400`:

```json
{
  "error": {
    "message": "Validation failed.",
    "fields": {
      "customerEmail": "Enter a valid customer email."
    }
  }
}
```

Unknown tickets use HTTP `404`.

## Design choices

- **SQLite:** persistent local database without an external service.
- **Express:** lightweight REST API with clear route responsibilities.
- **React:** component-based UI and straightforward state management.
- **Server-side querying:** filtering, search, ordering and pagination happen in the backend as required.
- **Automatic timestamps:** generated by the backend.
- **No authentication:** omitted because it is outside the required scope.

## Assumptions and known limitations

- A support team member can view and update tickets without authentication.
- SQLite is intended for local/demo use rather than high-concurrency production workloads.
- No file attachments, comments, authentication, email integration, or deployment configuration are included because they are outside scope.
- Search is a case-insensitive substring search.
- Ticket timestamps are stored in ISO format and formatted using the browser's local timezone.
- The summary endpoint intentionally ignores active list filters and always counts the entire dataset.
